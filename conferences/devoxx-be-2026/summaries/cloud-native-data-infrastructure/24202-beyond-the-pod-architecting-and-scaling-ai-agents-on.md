# Beyond the Pod: Architecting and Scaling AI Agents on Kubernetes

Abdellfetah SGHIOUAR · Conference · Cloud Native, Data & Infrastructure

## TL;DR

Mapping one AI agent to one Kubernetes Pod wastes compute because agents sit idle waiting on LLM responses or human approval, and their multi-gigabyte images pull too slowly to start on demand. Agent Substrate, an open-source multiplexer from Google, decouples logical agents (actors) from pre-warmed Pods (workers), adding suspend/resume with memory and filesystem snapshots, sub-second activation, sandboxing, and cross-node teleportation.

## Key takeaways

- One agent per Pod is wasteful: agents idle while waiting for the model or a human, so parking them and multiplexing many onto a shared warm pool preserves compute.
- Agent images are tens of gigabytes, which makes pull-on-start too slow; pre-warmed worker Pods with dependencies baked in keep activation under 500 ms.
- Suspend/resume preserves volatile memory and filesystem state, so an HTTP counter, a shell session, or a Jupyter kernel continues exactly where it stopped.
- The Kubernetes API server and etcd are too slow for the activation path, so Agent Substrate runs its own control plane API plus PostgreSQL for state.
- Agents ship as plain OCI containers and run sandboxed (gVisor, Firecracker, Kata) inside worker Pods selected by RuntimeClass.
- Scale the worker pool with a standard HPA plus cluster autoscaler; the morning cold start after a scaled-to-zero night is the accepted trade-off.

## Notes

### [00:34](https://youtu.be/3bIiAoYtAPs?t=34) Setup: AI-made slides, Agent Sandbox background

SGHIOUAR warns the slides were generated by NotebookLM and asks the audience to listen rather than read. He works as a Google Cloud developer advocate at the Kubernetes and agentic AI intersection. The work started with Agent Sandbox, open-sourced months earlier, which he pre-announces will be donated to the CNCF; it runs on any Kubernetes, not only GKE.

### [02:07](https://youtu.be/3bIiAoYtAPs?t=127) Why Pods are the wrong unit for agents

Agents idle most of their lives for two reasons: waiting for the LLM to respond, or waiting for human-in-the-loop approval. Kubernetes assumed Pods run backend code that serves traffic continuously. Two consequences follow: a Pod per agent burns resources on idle processes, and pulling a tens-of-gigabytes agent image from a registry on every start takes seconds, which breaks on-demand scheduling.

### [05:47](https://youtu.be/3bIiAoYtAPs?t=347) Agent Substrate: actors multiplexed over workers

Agent Substrate is an orchestration layer between Kubernetes and agents. Pre-provisioned worker Pods supply compute; actors (agents) are scheduled onto them only while running. Wake-up happens two ways: a monitor notices a looping agent needs to run, or the atenet router receives an HTTP/gRPC request for a sleeping actor. He concedes the warm pool itself consumes compute and recommends an HPA over the workers, accepting a seconds-long cold start on quiet mornings as cheaper than a thousand idle Pods.

### [08:56](https://youtu.be/3bIiAoYtAPs?t=536) Performance envelope and components

Claimed numbers: activation under 500 ms, 500 activations per second through the controller, and teleportation of a running agent across nodes with state preserved via S3-compatible storage (GCS in the demos). Five components: the control-plane API, the atenet router, a node-level snapshot/state-transfer agent, the microVM sandbox layer (gVisor, Firecracker, Kata, anything exposed as a RuntimeClass), and PostgreSQL, chosen because etcd cannot hit the activation latency.

### [13:39](https://youtu.be/3bIiAoYtAPs?t=819) Demo setup: control plane, worker pools, `kubectl ate`

On a GKE cluster he shows the substrate pods (API server, controller, snapshot agent, router, egress, PostgreSQL) and worker pools instantiated from templates. Platform teams bake shared dependencies into pool images so each agent stays small. All interaction goes through the `kubectl ate` plugin against the substrate API, not the Kubernetes API.

### [15:13](https://youtu.be/3bIiAoYtAPs?t=913) Demos: counter, shell, and Jupyter survive suspend/resume

An in-memory HTTP counter reads 5, is suspended, then a request through the router wakes it and the counter reads 6, then 7 after a second cycle: volatile memory survived. An interactive Alpine shell gets a file written to `/root`, exits into suspension, and a later command prints the file back: the filesystem survived. A Jupyter notebook with `x = 42` is suspended mid-session; after refresh, the notebook file and the variable value are intact and the second cell runs. He adds that GPU memory can be preserved under gVisor so model weights stay loaded.

### [25:53](https://youtu.be/3bIiAoYtAPs?t=1553) Atenespaces and multi-tenant sharing

Actors are not CRDs, so substrate has its own grouping primitive, atenespaces (`-a` flag), for multi-tenancy. Two agents from different templates and spaces wake through the router and land on workers in the same `shared-pool`, each visible with its actor count, CPU, and memory. The teleportation demo fails to render on screen ("just believe me, we can do teleportation").

### [31:41](https://youtu.be/3bIiAoYtAPs?t=1901) Framework-agnostic, and the scheduler-on-scheduler question

Anything that runs as a process works: LangChain, Google ADK, kagent, MCP servers, Codex, OpenCode. To the objection that this is just another scheduler on Kubernetes, he cites Tim Hockin's answer from his podcast: the layering is deliberate, and substrate primitives may migrate into Kubernetes over time. He names production users: Anthropic scaling to millions of agents (a KubeCon talk), and Lovable on GKE meeting a 30-second account-to-workspace requirement that fat-image pulls could not hit. Both interviews are on the Kubernetes Podcast by Google.

### [35:22](https://youtu.be/3bIiAoYtAPs?t=2122) Q&A

The "agent" naming is admitted hype. Agents ship as ordinary OCI containers, live-injected into worker Pods. Suspension can be manual, router-driven, monitor-driven, or self-requested by the agent calling the API. Missing capacity is handled the Kubernetes-native way (HPA plus cluster autoscaler); there is no agent queue today, though the reconciler keeps retrying. KEDA is unused for lack of GKE support; Knative plus sandboxing is a fair comparison. Solo.io's kagent runs inside, and Anthropic contributes to the project.

## Tools, libraries and specs

- Agent Sandbox (predecessor project, sandboxing layer)
- gVisor, Firecracker, Kata Containers via RuntimeClass
- PostgreSQL as substrate state store; S3-compatible storage (GCS in demos) for snapshots
- HPA and cluster autoscaler for worker-pool scaling
- LangChain, Google ADK, kagent (Solo.io), MCP servers, Codex, OpenCode, Antigravity CLI, Jupyter
- GKE, KEDA, Knative, Cloud Composer, Lovable, Gemini Enterprise Agents Platform

## Who should watch

Platform engineers running coding agents or agent fleets on Kubernetes gain the most, especially anyone sizing idle capacity or sandboxing untrusted agent code. Kubernetes-curious developers get a clear mental model of actors-over-workers. Skip it if you want substrate internals: the snapshot mechanism and router wake-up path are named, not explained.
