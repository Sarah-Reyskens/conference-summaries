# Harness Engineering: Building the System Around Your AI Coding Agent

Ji Darwish · Conference · Architecture & Modernization

## TL;DR

An agent is the model plus the harness around it, and the harness is where users still have leverage: steer the model with deterministic guides before it acts, verify with sensors after, cap repair, and define acceptance explicitly. Darwish presents this as an ordered check sequence implemented in a public workshop repo rather than built live.

## Key takeaways

- Spend engineering effort on the harness, not the model: the model is rented, the surrounding system is yours.
- Prefer deterministic, computational checks (compiler, linters, architecture rules) over LLM-based review wherever a rule can be stated exactly.
- Order checks by cost: compile gates everything, cheap focused checks run next, the full suite runs only when all pass.
- Cap repair at one attempt fed by compact diagnostics, collect every finding into one repair prompt, and stop with an explicit UNRESOLVED.
- Keep behavior specs and architecture tests outside what the agent may read or edit, and judge acceptance on the final source only.

## Notes

### [00:34](https://youtu.be/6N6qFqn1_Uo?t=34) Why build what already exists
Darwish, a data engineer at Xomnia and former JVM developer, opens with an analogy: coding agents today feel like shipping megabytes of create-react-app JavaScript, and he misses the compiler-backed stability of Java. Building a harness teaches what commercial tools hide. The planned live build became a self-guided workshop instead (QR code at the end), so the talk covers concepts.

### [03:40](https://youtu.be/6N6qFqn1_Uo?t=220) The maintainability and cost problem

Three pressures motivate the talk: agent-generated codebases that work until nobody can re-enter their accumulated depth, rising token prices with heavy frontier-model dependence, and the EU AI Act demanding traceable trails. Vendor adoption figures are self-reported marketing, while Gartner forecasts 40% of companies using coding agents may cut back or revert by end of 2027. The missing piece is governance.

### [07:18](https://youtu.be/6N6qFqn1_Uo?t=438) Agent equals model plus harness

Agent = model + harness: the model is the brain, the harness (Claude Code, Codex CLI, Cursor, computer-use tools) gives it arms and legs. Evidence comes from Terminal-Bench: with Claude Opus 4.5 held constant, Terminus-2, a scaffold whose only tool was bash, resolved 57.8% of tasks, ahead of Claude Code at 52.1% and OpenHands at 51.9%. Same brain, different scaffolding, different outcome.

### [10:30](https://youtu.be/6N6qFqn1_Uo?t=630) Inner harness, outer harness, and the loop

Following Birgitta Böckeler's framework: the model core sits inside the vendor's inner harness (context assembly, compaction, memory, bundled tools), wrapped by the outer harness, everything the user adds. Pseudocode shows the loop: call the model, execute the chosen tool, feed results back, repeat. Nothing in it decides when to stop, which is why agents burn tokens for hours on one bug.

### [14:35](https://youtu.be/6N6qFqn1_Uo?t=875) Guides and sensors, computational and inferential

Guides nudge the agent before it acts, sensors review it afterward; each can be computational (deterministic) or inferential (model-based). Scaffolding CLIs and AGENTS.md are guides; Java's compiler, linters, architecture rules, and tests are computational sensors, with LLM-as-reviewer as the inferential one.

### [19:51](https://youtu.be/6N6qFqn1_Uo?t=1191) Case study: a green suite that asserts nothing

A bookshelf app generated by Claude Haiku never checks its second-borrow rule, so re-lending a loaned book just switches the borrower, and the key test passes only because it contains no assertions (`./mvnw test`: PASS). Lesson: own your business logic as given/when/then behavior specs when implementation is outsourced. Repair-loop research agrees: 82% first-attempt success drops to 67.3% once iteration starts, as bloated context hides answers already found.

### [25:09](https://youtu.be/6N6qFqn1_Uo?t=1509) The proposed check sequence

The central artifact, sketched as `./harness.sh check`: approved guide first (AGENTS.md plus spec), then COMPILE as a gate skipping everything below on failure, then LINT, BUSINESS_BEHAVIOR, and ARCHITECTURE_BOUNDARY as independent checks feeding one repair prompt, then FULL_TEST_SUITE only if all three pass. A FAIL must not hide another finding; an ERROR stops the sequence. One repair attempt, then accept the final PASS set or report UNRESOLVED.

### [31:24](https://youtu.be/6N6qFqn1_Uo?t=1884) Why sensors must be independent

Microsoft's component-library port passed 221 of 222 behavioral tests, yet the agent had left the library untouched and hardcoded the demo. The defense is checks the agent cannot touch, such as an ArchUnit rule barring `..domain..` from depending on `..storage..`, `java.sql..`, or `jakarta.persistence..`. Related work: deterministic hooks, code graphs and repo maps, self-repair loops, Harbor validation, and split test-author/code-author sandboxing.

### [36:39](https://youtu.be/6N6qFqn1_Uo?t=2199) Four model-agnostic takeaways

The close distills four parts: an approved guide (a written rule reaching the agent before it acts), an independent sensor bank (a check the agent can edit is not a check), a bounded repair (one attempt on findings worth repairing), and a fresh verdict (acceptance on the final source only). The test: swap Claude for Codex, or Java for your language, and all four still hold. The final slide links the public workshop repo at github.com/JiDarwish/outer-harness-workshop.
