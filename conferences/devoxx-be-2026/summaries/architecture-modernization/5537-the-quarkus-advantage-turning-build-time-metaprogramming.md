# The Quarkus advantage: Turning build-time metaprogramming into runtime performances
Mario Fusco, Georgios Andrianakis, Francesco Nigro · Deep Dive · Architecture & Modernization

## TL;DR
Quarkus moves framework work (annotation scanning, dispatch, serialization) from runtime to build time by indexing the application with Jandex and generating bytecode with Gizmo, eliminating reflection from hot paths. The second half is a performance investigation where a generated Jackson serializer first lost to reflection, and fixing it required tracing through JIT inlining, register spilling, and String::charAt profile pollution into upstream Jackson patches.

## Key takeaways
- Reflection costs are unstable over time: reflection metadata lives in soft references the GC can wipe, and pre-JDK 18 reflective calls change shape after 15 invocations (the inflation threshold), so reflective hot paths never settle.
- Quarkus build steps consume and produce build items, forming a dependency graph that runs at build time; extension authors reuse existing build items (e.g. the REST endpoint index) to generate code instead of scanning at runtime.
- Replacing an interface dispatch loop with a generated tableswitch dispatcher turned megamorphic handler calls into monomorphic ones and avoided instanceof-driven type pollution.
- A generated, reflection-free Jackson serializer initially performed worse than Jackson 3's MethodHandle-based reflection because inlining the generated code into a large method caused JIT register spilling.
- A single eagerly created non-ASCII String in Jackson (RFC1123 date fallback) poisoned the shared String::charAt profile and suppressed loop unrolling in unrelated string loops; making it lazy plus an escape-scan fast path unlocked 4x unrolling.
- Performance decisions expire: the same generated serializer that clearly won on JDK 17 / Jackson 2 lost on JDK 25 / Jackson 3, so benchmarks must be re-run as the JDK and libraries evolve.

## Notes

### [02:12](https://youtu.be/SgK0zMNayq0?t=132) Build time versus runtime: the core principle
Georgios Andrianakis opened with the framing the whole talk returns to. Traditional frameworks do nothing at build time except produce a jar, then at startup scan the classpath, read annotations and XML, and assemble the application. Quarkus does that work once during `mvn package`: the classpath cannot change at runtime, so annotations and descriptors known at build time are baked into the jar. Avoided work means faster startup, lower memory, and a much easier path to GraalVM native image. He noted Quarkus has held this principle unchanged since 2019.

### [04:47](https://youtu.be/SgK0zMNayq0?t=287) How reflection works under the hood (pre-JDK 18)
Francesco Nigro walked through old-school reflection cost by cost. Reflective metadata is parsed from class files into metaspace and cached in a `reflectionData` soft-reference field on `Class`, so GC decisions can wipe it and force re-reads. Invocation below 15 calls uses a native accessor; past the inflation threshold the JVM generates bytecode (extra CPU and garbage in the application's steady state). Field access went through `sun.misc.Unsafe`. Caller checks are cached in a single-slot cache that flip-flops under multiple callers, forcing a stack walk per call. Callee checks (receiver type, argument types, boxing/widening rules) run on every call with no cache. Final fields of trusted JDK classes add further special cases.

### [16:16](https://youtu.be/SgK0zMNayq0?t=976) JDK 18+ reflection on MethodHandles
Since JDK 18, reflection is built on MethodHandles. Performance was explicitly a non-goal of that refactoring; any speedup was incidental. There is no more inflation threshold (the native call happens once at JVM bootstrap), field access moved from Unsafe to VarHandles (more secure, more costly), and trusted final fields stay read-only even after `setAccessible(true)`. The soft-reference metadata behavior and all visibility/argument/receiver checks are unchanged. A slide summarized the two eras as Metadata → Checks → generated bytecode versus Metadata → Checks → MethodHandle.

### [22:05](https://youtu.be/SgK0zMNayq0?t=1325) Demo: generated REST endpoint invokers
Mario Fusco showed the simplest metaprogramming example. Instead of discovering `@Path` methods at startup and invoking them reflectively, Quarkus generates one synthetic class per endpoint (e.g. `PersonResource$get...EndpointInvoker`) implementing an invoker interface with a direct downcast and plain method call. In the IDE he ran a build with generated bytecode dumped to `target/`, opened a generated invoker, and showed a live request stack containing the direct `invoke` call with no reflective frames. With a reflective framework the same stack would show a long chain of reflection calls.

### [28:32](https://youtu.be/SgK0zMNayq0?t=1712) Build steps, build items, Jandex, Gizmo
The build-time machinery has three parts. Processors hold methods annotated `@BuildStep`; each step consumes build items and produces build items, and Quarkus derives a dependency graph so steps run in the right order. Debugging a build live, Fusco showed a breakpoint inside the RESTEasy Reactive processor method that indexes endpoints. The two libraries doing the heavy lifting: Jandex, which parses bytecode into an annotation/type index without loading classes (the offline equivalent of a runtime class scanner), and Gizmo, a Java-friendly bytecode-generation DSL in which each statement maps to the generated class, constructor, interface, and method. The same endpoint index feeds multiple consumers: the invoker generator and, later in the talk, the Jackson serializer generator.

### [48:36](https://youtu.be/SgK0zMNayq0?t=2916) The REST handler chain: from megamorphic calls to a generated dispatcher
Andrianakis explained RESTEasy Reactive as a "context object pattern": one large request-context class plus a chain of about 18 `ServerRestHandler` implementations (matrix params, query params, security, filters, invocation, serialization, observability), each stuffing results into the context. Calling `handler.handle(ctx)` through the interface is a megamorphic call. The first optimization downcast each handler to its concrete type (monomorphic `invokevirtual`), but the resulting instanceof/if-else chain suffered from type pollution, a known JDK performance pitfall. For this talk he finally implemented what Nigro had suggested four years earlier: at build time, assign each handler a constant and generate a per-endpoint dispatcher that switches on it, compiling to a `tableswitch` the JIT optimizes well. Extensions with unknown handlers fall back to the megamorphic call. He also admitted Quarkus itself uses reflection at build time to invoke `@BuildStep` methods, where performance does not matter.

### [69:41](https://youtu.be/SgK0zMNayq0?t=4181) Generating GraalVM metadata and substitutions
Because GraalVM native image follows a closed-world principle, it needs JSON metadata (reflection, JNI, proxies, serialization) that is impractical to write by hand for a framework; Quarkus generates it from build items in a dedicated build step. The same generation approach covers GraalVM `@Substitute` classes (e.g. zeroing Netty's zstd constants when that library is absent, disabling OpenSSL) and even generated `Feature` implementations that tell GraalVM which classes to initialize at build time. Generated substitutions are rare (perhaps 1 in 100), but the point is that build-time knowledge plus generation can produce anything: bytecode, JSON, or source.

### [78:37](https://youtu.be/SgK0zMNayq0?t=4717) Bytecode transformation: the Netty process-ID case
Netty still targeted Java 6, so its `DefaultChannelId` read the process ID through old-school reflection on `ProcessHandle` (only available since Java 9), behind a version check. A flame graph showed that call dominating startup cost. Since even Quarkus 3 required Java 17, the check was dead weight, so Quarkus ships a Gizmo bytecode transformer (via a `BytecodeTransformerBuildItem`) that rewrites the method into a direct `ProcessHandle.current().pid()` call. The speakers stressed the policy: always try to fix upstream first (Nigro is a Netty committer and opened the issue that morning), transform only what measurements justify, and accept the maintenance risk when upstream targets older JDKs. Ten such 4 ms startup fixes add up to tens of milliseconds, and identical libraries end up with roughly half the RSS under Quarkus versus competitors.

### [90:22](https://youtu.be/SgK0zMNayq0?t=5422) Reflection-free Jackson serializers, generated
Fusco turned to third-party reflection: Jackson's default serialization discovers bean properties reflectively. Jackson allows hand-written `StdSerializer` subclasses that call getters directly and register on a module, so Quarkus generates exactly such serializers at build time, reusing the REST endpoint index to learn which types need them and walking the object tree (an `ExtendedPerson` pulls in `Address` and `Car` serializers too). He showed a generated serializer in the IDE. The feature is opt-in via an application property because Jackson's many customization annotations created a long tail of corner cases, and because of the performance story that follows.

### [101:29](https://youtu.be/SgK0zMNayq0?t=6089) The benchmark that went backwards
The benchmark: a REST endpoint returning 20 `ExtendedPerson` objects to emphasize serialization, driven by Hyperfoil on JDK 25 with a Quarkus 4 snapshot and Jackson 3. The generated serializer scored slightly below Jackson's reflection path (about 144,000 requests/s for reflection). Two years earlier, on JDK 17 with Quarkus 3 and Jackson 2, the generated code had won clearly. In between, reflection moved to MethodHandles and Jackson 3 rewrote its accessors around `MethodHandle.invokeExact` with a single-slot accessible cache, closing most of the gap. The user code was identical in both cases; only the platform shifted.

### [112:30](https://youtu.be/SgK0zMNayq0?t=6750) The flame graph: writeString at 15% versus 50%
Profiling with async-profiler showed the same library method, `UTF8JsonGenerator.writeString`, costing 15.61% of samples under Jackson's serializer but 50.53% under the generated one. The generated path had inlined the call (light-blue frames), which should have made it faster, not slower. That contradiction handed the investigation to Nigro.

### [119:27](https://youtu.be/SgK0zMNayq0?t=7167) Inlining, register spilling, and String::charAt profile pollution
Nigro's assembly-level analysis found three stacked effects. First, inlining every per-field `writeString` into the large generated `serialize` method bloated the caller's state so the JIT spilled registers to the stack on the hot path (memory access costs roughly 3x a register hit), visible only in the compiled parent's assembly. Second, the char-at-a-time escape loop was not being unrolled because of profile pollution: HotSpot keeps `String::charAt` telemetry in the callee, and one eagerly created non-ASCII String in Jackson (an RFC1123 date-formatting fallback allocated with every `ObjectMapper`) poisoned the latin1/UTF16 branch for the whole JVM. Third, the per-character escape-table load plus bounds checks consumed the JIT's unrolling budget, capping unrolling at 2x. Disabling inlining via compiler directives confirmed the diagnosis but was rejected as a global, native-image-unfriendly hack.

### [131:39](https://youtu.be/SgK0zMNayq0?t=7899) The fixes, upstreamed to Jackson
Two Jackson contributions resulted. Making the fallback date String lazy removed the `charAt` profile poisoning; replacing the per-character escape-table load with comparison-based checks in an overridable escape-scan fast path (FasterXML jackson-core #1680/#1681/#1682, targeting 3.1.3) unlocked 4x loop unrolling, cutting spills from one per char to one per four chars on ASCII input. The escape fast-path work was prototyped with Claude Code assistance, per the PR screenshot.

### [136:22](https://youtu.be/SgK0zMNayq0?t=8182) Results and lessons learned
End to end, the fixes delivered about 8% throughput improvement on a test where serialization was deliberately prominent but I/O still dominated; a JMH nano-benchmark of serialization alone showed 40-50%. The reflective path improved too, since loop unrolling benefited both. The closing slide's lessons: performance is a moving target, so reevaluate decisions over time; human-readable generated bytecode is not necessarily JIT-friendly; not all JIT decisions (like inlining) improve code; and the Quarkus team fixes the ecosystem when needed rather than shipping a default they cannot defend. The feature stays opt-in until the ecosystem pieces land.

## Tools, libraries and specs
- Quarkus 3 / 4 (beta 1), extensions model with build steps and build items
- Jandex (offline annotation/bytecode indexing) and Gizmo / Gizmo 2 (bytecode generation DSL)
- Jackson 2 / Jackson 3, `StdSerializer`, `ObjectMapper`, FasterXML jackson-core #1680/#1681/#1682
- OpenJDK 17 / 21 / 25, JEP 416 (JDK 18 reflection on MethodHandles), Class-File API, JIT (inlining, loop unrolling, register allocation), Flight Recorder reflection event
- GraalVM native image (closed-world assumption, substitutions, Feature API, build-time class initialization)
- Netty 4.1/4.2 (`DefaultChannelId`, zstd/OpenSSL handling), RESTEasy Reactive handler chain
- async-profiler (flame graphs), JMH, Hyperfoil (load generator), hsdis-style JIT assembly dumps
- `String::charAt` compact-strings latin1/UTF16 split; type pollution / profile pollution (HotSpot-shared callee profiles)

## Who should watch
Framework and library authors, performance engineers, and Quarkus users who want to understand what build-time extension code buys and costs. Java developers curious about JIT behavior (inlining trade-offs, profile pollution, unrolling budgets) get a rare end-to-end case study with assembly-level evidence. Skip it if you want a Quarkus getting-started guide or application-level tuning advice; this is internals and compiler interaction throughout.
